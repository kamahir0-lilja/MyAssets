# 利用例・仕様から進める

Status: Active

1. **利用**: 変更後に利用側（C# または Unity CLI）が実行する短い呼び出しと、操作前・操作後の状態を書く。
2. **仕様**: [正本](../specs/my-assets.md) に期待結果と安定 ID を置く。成功だけでなく、未ログイン、未ダウンロード、取消、不正引数、内部 API 互換性を確認する。
3. **レビュー**: 仕様を書き終えてから別 pass で読む。主張が検証できるか、非同期イベントの未購読解除やデッドロックがないかを確認する。
4. **受け入れテスト**: 利用者の結果を再現するテストを先に追加する。外部通信や未ログイン等の失敗は内部の backend seam で固定し、実機 Unity の内部 API 解決は実アセンブリに対する probe テストで検証する。
5. **実装**: テストを通し、Core 層（Pipeline 非依存）と Pipeline 層（`[CliCommand]` 定義）の責務分離を保つ。
6. **検証**: 静的検査（`scripts/validate.py`）および Unity EditMode tests を確認する。テスト成功と全 Unity バージョン保証を混同しない。
7. **記録**: 仕様 ID、対象ソースの fingerprint、環境、結果、制約を evidence に残す。生ログは artifacts に置き、公開したとみなさない。

採用済み仕様の意味を変える場合だけ [変更ひな形](../changes/_template.md) を使う。
依頼内の設計判断は理由を残して自律的に採用できる。各段階でのユーザー承認や別エージェントは必須ではない。
重大な範囲拡張や未許可の公開など、実際に判断が必要な境界だけ確認する。
仕様は Adopted、検証結果は evidence に分ける。テストが存在するだけで検証済みにしない。
